# Modelling scope and networking concepts

NetSleuth's core runs entirely on a deterministic virtual lab. This document states
**exactly** which protocol behaviours are modelled, which are simplified, and which
are absent — because a diagnostic tool that overstates its model is worse than one
that states its limits.

Everything here is generated by `backend/app/lab/simulator.py` and
`backend/app/lab/routing.py`, and is asserted by the tests in
`backend/tests/unit/test_lab_simulator.py`.

---

## 1. Layering

The simulator is organised as seven layers, each a small set of pure functions:

| Layer | Question it answers | Module entry point |
|---|---|---|
| 1. Forwarding | Is there a usable path, and where does it break? | `LabSimulator.forwarding_state` |
| 2. Network (ICMP-style) | Does an echo request get a reply, how fast, and how reliably? | `LabSimulator.icmp_probe` |
| 3. DNS | Does the name resolve, and if not, why not? | `LabSimulator.dns_probe` |
| 4. Path trace | Hop by hop, how far does the path actually go? | `LabSimulator.traceroute` |
| 5. Transport (TCP) | Does the handshake complete, get refused, or time out? | `LabSimulator.tcp_probe` |
| 6. Path MTU | Which packet sizes complete the round trip? | `LabSimulator.mtu_probe` |
| 7. Application | Does the service answer a health check? | `LabSimulator.service_probe` |

Keeping the layers separate is what lets a probe be thin and a test target one
behaviour at a time.

## 2. IP forwarding and routing

**Modelled**

- Nodes are `host`, `router`, `dns_server` or `app_server`, each with a unique IPv4
  address (validated with `ipaddress`), a display name and layout coordinates.
- Links are *symmetric* and have `up`, `latency_ms`, `packet_loss_rate`, `mtu_bytes`
  and display-only `bandwidth_mbps`.
- Routers forward on the **lowest-hop-count** path, computed with Dijkstra where the
  heap key is `(hops, link-id sequence)`. The link-id tie-break makes the result
  fully deterministic for a fixed topology instead of depending on dictionary
  ordering.
- Only links with `up = True` are traversable, so a failed link removes the path
  exactly as a failed physical link would.
- A router's forwarding table is *derived* from those paths, so undoing a fault
  automatically restores the original forwarding behaviour. The Lab page renders
  these tables.
- Hop count is real: it is `len(path.nodes) - 1` and it drives both the modelled
  RTT (one processing cost per transit router) and the traceroute hop list.

**Simplified or absent**

- **No dynamic routing protocol.** No OSPF/BGP, no convergence, no alternative-path
  failover. Both topologies are deliberately non-redundant (no parallel links
  between the same pair of routers), so a link failure really does remove the path —
  which is what makes traceroute-based localization meaningful. An operator
  expectation of automatic reroute does not hold in this lab.
- **No subnets or longest-prefix matching.** The topology is a graph, not a set of
  prefix advertisements. `10.10.0.0/24`-style addresses are readable labels.
- **No ARP, no L2 switching, no VLANs, no IPv6.**
- **No queueing or congestion.** `bandwidth_mbps` is display metadata only and is
  explicitly documented as not modelled.

## 3. ICMP-style reachability

**Modelled**

- Four *selectors*, each with its own evidence value: the destination, the source's
  default gateway, the DNS resolver, and an independent control destination in the
  destination's own segment.
- `ICMP_ECHO_COUNT` (4) echo requests per probe. A packet survives only if **every**
  link on the path lets it through, so end-to-end delivery probability is the product
  of the per-link survival probabilities — the geometry a real `ping` sees.
- RTT is `2 × (Σ link latency + per-hop processing) + jitter`, so RTT grows with hop
  count as it does on a real path. Mean RTT above `ICMP_HIGH_LATENCY_MS` (150 ms) is
  reported as `REACHABLE_SLOW`.
- Outcome vocabulary: `REACHABLE`, `REACHABLE_SLOW`, `PARTIAL_LOSS`, `TIMEOUT`,
  `UNREACHABLE_NETWORK`, `UNREACHABLE_HOST`.
- **ICMP error semantics are distinguished.** A router's refusal produces
  `UNREACHABLE_NETWORK`; a failure on the final link produces `UNREACHABLE_HOST`; a
  withdrawn route produces a **silent `TIMEOUT`**. This difference is the main
  discriminator between the link-failure and routing-failure hypotheses.
- **A blocked echo request is not treated as proof of a dead host.** When the path
  is usable but the target does not answer, the observation says so explicitly and
  the evidence statement is marked `weak` and labelled as possibly filtered —
  because that is what a filtered ICMP reply means in practice.

**Absent**

- No real ICMP encoding, no packet capture, no raw sockets, no TTL manipulation on a
  real network.

## 4. DNS

**Modelled**

- Resolvers are nodes with a zone (`dns_records`) and an administrative flag
  (`resolver_enabled`) that models a daemon outage independently of link state.
- Outcome vocabulary: `RESOLVED`, `RESOLVED_SLOW`, `TIMEOUT_RESOLVER`, `NXDOMAIN`.
- **The resolver answering NXDOMAIN is distinguished from the resolver not
  answering at all.** NXDOMAIN means the resolver was reachable and replied — the
  strongest single DNS signal available. `TIMEOUT_RESOLVER` is compatible with both
  a daemon outage and an unreachable resolver host, which is why the resolver-host
  ping exists and why `DNS_FAILURE` is *not* treated as resolved by it.
- Names not in the zone produce NXDOMAIN rather than a timeout.
- A resolver outage does not prevent testing the destination IP directly: the ICMP,
  TCP, MTU and service probes never depend on name resolution.

**Absent**

- No recursive resolution, no caching, no DNSSEC, no CNAME chains, no per-record TTL
  behaviour, no upstream forwarding.

## 5. Traceroute / TTL-limited probing

**Modelled**

- The trace walks the **nominal** path (as if every link were up) hop by hop, and
  records, per hop, the TTL, node id, name, IP, RTT and whether it responded.
- `TRACEROUTE_MAX_TTL` caps the trace; per-hop loss is sampled **independently** so
  one lossy link shows up as that single hop failing rather than silencing every
  subsequent hop.
- Outcome vocabulary: `COMPLETE`, `COMPLETE_WITH_SUPPRESSED`, `PARTIAL`,
  `NO_FIRST_HOP`.
- A trace that reaches the destination while some intermediate hops stay silent is
  `COMPLETE_WITH_SUPPRESSED`, and the evidence says that routers can suppress
  TTL-expired replies, so a single silent hop is suggestive rather than conclusive.
- `PARTIAL` records `last_responding_node` and `suspect_link`, which is what the
  localizer turns into "the fault is on link X".

**Absent**

- No real TTL field, no ICMP time-exceeded generation, no path variation between
  probes, no ECMP.

## 6. TCP

**Modelled**

- Per-host, per-port policy: `open`, `drop`, `reject`, `service_down`.
- Outcome vocabulary: `CONNECTED`, `CONNECTED_SLOW`, `TIMEOUT_DROP`,
  `REFUSED_NETWORK_POLICY`, `REFUSED_NO_LISTENER`, `UNREACHABLE`.
- **Silent drop and active rejection are different outcomes**, and both are
  different from a reset from the destination host. A SYN timeout means the packet
  vanished (filter that drops, or loss); an immediate refusal means something
  answered and refused it; a reset from the host means the host is up but nothing is
  listening.
- Handshake RTT is modelled from the same path latency, and above `TCP_SLOW_MS`
  (250 ms) the outcome is `CONNECTED_SLOW`.
- Only a **single configured port per probe** is ever tested. There is no port
  range, no subnet sweep and no scan of any kind, in the simulator or anywhere else.

**Absent**

- No real three-way handshake, no sequence numbers, no window scaling, no retransmit
  timers, no SYN backlog, no real sockets.

## 7. Path MTU

**Modelled**

- Path MTU is `min(link.mtu_bytes)` over the traversed links.
- A documented ladder of datagram sizes (`64, 128, 256, 512, 1000, 1400, 1472, 1500`)
  is probed. Each size is sent `MTU_PROBE_ATTEMPTS` (3) times.
- A size that fits the path MTU can still be lost; a size above it **must** fail.
- Whether the sender is told is modelled explicitly with `suppress_frag_needed`:
  when set, oversized datagrams are discarded **without** an ICMP
  fragmentation-needed reply — a path-MTU black hole. When clear, the ICMP error is
  returned and the outcome is `LIMITED_REPORTED` instead of `LIMITED_DROP`.
- Outcome vocabulary: `FULL_PATH_OK`, `LIMITED_DROP`, `LIMITED_REPORTED`,
  `INCONCLUSIVE_LOSS`, `INCONCLUSIVE_NON_MONOTONE`, `UNREACHABLE`.
- **Two honest inconclusive outcomes.** `INCONCLUSIVE_NON_MONOTONE` means a size
  inside the path MTU *succeeded* while a smaller size failed on every attempt. A
  path-MTU boundary is monotone by definition, so this pattern cannot be an MTU
  limit and is reported as evidence of **packet loss**. `INCONCLUSIVE_LOSS` means
  the ladder is not interpretable but the pattern is still MTU-compatible. Without
  these two outcomes the ladder would misattribute lossy links to the MTU — which is
  exactly the baseline's dominant failure in the evaluation.

**Absent**

- No actual fragmentation or reassembly. `MTU_MIN` (68) and `MTU_MAX` (65535) bound
  validation; RFC 791's 576-byte minimum reassembly buffer and RFC 1191's PMTUD
  procedure are the conceptual references (see `references.md`).

## 8. Application service

**Modelled**

- Each app server exposes named TCP services with a port, a `healthy` flag and a
  declared response size.
- Outcome vocabulary: `HEALTHY`, `DEGRADED_STALL`, `UNAVAILABLE_REFUSED_POLICY`,
  `UNAVAILABLE_REFUSED_NO_LISTENER`, `UNAVAILABLE_TIMEOUT`, `UNREACHABLE`.
- The layer is only reached once the network and transport layers are viable, so a
  service check reports `UNREACHABLE` rather than a fabricated application error when
  the path is broken.
- A `health` response above the path MTU is affected by the MTU layer, which is why
  `response_bytes` exists.

**Absent**

- No HTTP, TLS, protocol parsing, dependency checks, or application logs.

## 9. Determinism

All randomness comes from `LabSimulator.rng(tag)`, which seeds
`random.Random(f"netsleuth|{seed}|{tag}")`. Consequences:

- A fixed `(topology, active faults, session seed, probe tag)` triple always yields
  identical observations. A test asserts this for loss and latency faults across
  three independent constructions.
- Different seeds produce genuinely different loss patterns (asserted).
- Different tags give independent samples within one seed.
- The diagnosis tag is `f"{diagnosis_id}:{sequence_number}"`, so a re-run of the same
  diagnosis id and probe index reproduces its observation exactly, while a different
  diagnosis samples independently.

## 10. What "simulated" means in the output

- Every observation carries `mode: "SIMULATED LAB"`.
- Each step separately records `modelled_elapsed_ms` (the simulated protocol time,
  e.g. a timeout or an RTT) and `measured_wall_clock_ms` (how long the probe
  computation actually took). The UI and the exports label both, and the evaluation
  metrics use only the measured value — never the modelled one.
- `GET /api/v1/health` reports `live_probe_enabled: false` and the simulation mode
  string, so a caller can never mistake this build for one that probes a real
  network.
