# Demo script (3–5 minutes)

A walkthrough you can perform live. Everything shown comes from the running backend;
nothing in the UI is pre-filled sample data.

**Setup (once, before the demo)**

```bash
# terminal 1
cd backend && python3 -m uvicorn app.main:app --port 8000

# terminal 2
cd frontend && npm run dev
```

Open <http://127.0.0.1:5173>. Confirm the header shows `SIMULATED LAB` and a green
backend badge. If the badge is red, start the backend and reload.

---

## Demonstration A — DNS failure (about 90 seconds)

**1. Start with a clean, honest dashboard.**

Open **Overview**. Point out:

- every counter is `0` on a fresh install and the page says *"No lab sessions yet"* —
  there is no seeded demo data;
- the simulation label is in the header and the footer explains what it means.

**2. Create the campus topology.**

Go to **Network Lab** → *Create session from Small Campus Network*.

Walk the diagram while narrating:

- three client hosts, an access router, a campus router, a server-segment router, a
  DNS resolver, a web server and a database;
- each link label shows its simulated latency, MTU and loss — e.g. `2.5ms mtu1500`;
- the legend distinguishes node types by **shape and label**, not just colour;
- below, the *Derived forwarding tables* panel shows that routers have real derived
  next hops, and the *Link details* table shows every link's state.

**3. Inject the DNS fault.**

In *Fault injection*, choose the `DNS_FAILURE → Campus DNS Resolver (dns-1)` entry.
Note the preview naming the target and citing the description. Click *Inject fault*.

Point out in *Active faults*:

- it is a structured record: type, target, target kind, parameters, description;
- it is reversible — *Disable* and *Remove* are both available, and *Reset Lab* clears
  everything (with a confirmation).

**4. Run the diagnosis one step at a time.**

Go to **Diagnostic Workbench**. Confirm source `client-1`, destination `Campus Web
Server`, service `web`, budget 8, strategy *adaptive*. Click **Start diagnosis**, then
**Run One Step** three times.

After each step, narrate what the panel shows:

- the **next probe the planner selected**, with its expected information gain in bits,
  its relative cost, its EIG/cost score and the current belief entropy;
- the **reason sentence**, e.g. *"DNS lookup was selected because it is expected to
  remove 0.963 bits of uncertainty… The outcomes that would most change the ranking
  are NXDOMAIN … or TIMEOUT_RESOLVER …"*;
- the **alternatives table** — what it was compared against and why it lost;
- the **hypothesis ranking** with posterior bars and each hypothesis's prior;
- the **timeline entry**: outcome, evidence statements tagged
  `observation`/`reading`/`limitation` with a strength, the modelled simulated time
  and the measured compute time *separately*.

Key narration point after the DNS step: *the gateway and destination pings keep
succeeding while the name lookup fails.* That is the evidence which raises DNS and
lowers the path hypotheses.

**5. Finish it.**

Click **Run to Conclusion**. Then:

- the status badge becomes `confident`;
- the headline reads *Most likely cause: DNS_FAILURE …*;
- the **suspected component** panel says `node dns-1` with location confidence
  `strong`, and the topology highlights the resolver.

Click **Compare with Baseline**. Show the side-by-side table: the adaptive run used
fewer probes; the baseline ran a different order; the note states that only the order
differed.

**6. Open the report.**

Go to **Evidence & Report**. Show:

- supporting evidence, weakening evidence and *what the leading hypothesis does not
  explain* — three separate lists;
- the **likelihood impact** table: how much each observation moved each hypothesis;
- the full timeline with per-probe structured details expandable;
- the caveats, including the `SIMULATED LAB` label and the ground-truth isolation
  statement.

Click **Export Markdown** to download the report, and **Preview** to render it in the
page. Say explicitly: *this file is generated by the backend from the same stored
records this page renders.*

## Demonstration B — route failure and localization (about 75 seconds)

**1. Reset and inject a different fault.**

Back to **Network Lab**. Click **Reset Lab** (confirm). In *Fault injection*, choose
`ROUTE_BLACKHOLE → Campus Router <-> Server Segment Router → black-hole route to
Campus Web Server`. Inject it.

Explain the distinction: the link is still **up**; the route to the destination is
withdrawn. The packet is silently discarded — no ICMP error is generated.

**2. Diagnose.**

**Diagnostic Workbench** → **Start & run to conclusion**.

Show:

- the top hypothesis is `ROUTING_FAILURE`;
- the **localization**: the suspected component is `link l-campus-edge`, i.e. the
  specific link where the route was withdrawn, with the evidence showing the last
  responding hop and the link that brackets the fault;
- the timeline contains a *TTL-limited path trace* whose evidence names the last
  responding hop and states explicitly that *"a trace localizes a fault to a segment;
  it does not by itself prove whether the link is down or the route was withdrawn"*.

That last sentence is the point to dwell on: the engine reports what it can and cannot
conclude from a given observation, rather than overreaching.

**3. Contrast with a dead service.**

Reset, inject `SERVICE_DOWN → web on Campus Web Server (port 80)`, and run again. The
conclusion becomes `APPLICATION_SERVICE_FAILURE`, and the topology highlights the
**server**, not a link — because the network path was healthy the whole time and only
the application was not serving.

## Demonstration C — measured evaluation (about 60 seconds)

**1. Open Experiment Studio.**

Point out that the page shows *"No results yet — this page deliberately has no sample
data"*.

**2. Show the catalogue.**

Scroll to *Scenario catalogue and baseline sequence*: the 24 ground-truth scenarios
with their targets, parameters and expected causes, and the documented fixed order the
baseline uses. Mention that ground-truth labels are read only by the evaluator, after
each run.

**3. Run a small reproducible suite.**

Set *Runs per scenario* to 3, seed to `20261009`, click **Run experiment suite**. Point
out that the estimate panel showed the exact run count **before** executing.

**4. Read the results honestly.**

Show:

- the headline table side by side: adaptive vs baseline top-1, top-3, mean probes,
  coverage, inconclusive rate;
- the **per-fault-class** chart: this is where the interesting finding is. The baseline
  scores well on DNS/latency/port/service but poorly on MTU and link faults, because
  its fixed order reaches the MTU ladder last;
- the **confusion matrix** with counts, and the note that off-diagonal cells are real
  errors unless documented as an accepted confusion;
- the **completed run count** and the measured suite wall-clock time, with the explicit
  statement that elapsed time is simulator computation, not network latency.

**5. State the actual numbers from the last recorded run.**

440 runs (seed 20261009, 10 runs per scenario, budget 8):

| | adaptive | baseline |
|---|---:|---:|
| Top-1 | 99.6% | 71.4% |
| Mean probes | 4.20 | 7.00 |
| Coverage | 97.7% | 81.8% |
| Top-1 / MTU black hole | 100% | 0% |
| Top-1 / link failure | 100% | 25% |

Then state the limits plainly:

- the advantage is measured **inside this simulator**, and the likelihood model was
  written for the same protocol behaviour the lab implements, so model–model
  circularity applies;
- the adaptive strategy's measured *compute* time is higher (4.5 ms vs 2.1 ms) because
  planning costs more than a simulated probe; the probe-count saving is the meaningful
  efficiency claim here, and in a real network probe cost would dominate — but this
  evaluation cannot demonstrate that;
- packet loss is the hardest class (95% adaptive, with a 25% inconclusive rate), and
  that is a genuine limitation, not a rounding artefact;
- nothing here claims the result transfers to a real network. See
  `docs/limitations.md`.

**6. Export.**

Click **JSON**, **CSV** and **Markdown report** to show that the exports come from the
stored run records. Mention that a test asserts the metrics can be recomputed from the
database alone, so the API cannot be the only place the numbers exist.

## Closing statement

> NetSleuth implements an explainable probabilistic diagnostic engine: an explicit
> likelihood catalogue, a Bayesian belief updater with a full audit trail, and probe
> selection by expected information gain per unit cost — compared against a fixed-order
> baseline on stored run records. In this deterministic virtual lab the adaptive
> planner reached the correct cause in 99.6% of 440 runs using 4.2 probes, against
> 71.4% using 7.0 probes for the fixed order. The measurements are reproducible from
> the stored configuration, the engine cannot see the injected fault labels, and every
> observation is labelled SIMULATED LAB.

## Likely viva questions, with prepared answers

**Q: Why is a successful ping not treated as evidence that nothing is wrong?**
Because a probe is only informative about the layer it tests. The likelihood default
is deliberately near-neutral (0.9) for hypotheses a given probe does not address, so a
healthy echo request rules out a down link while leaving DNS, port, MTU and service
hypotheses untouched. A small default would make the engine "confident" after one
probe — the exact failure mode this design avoids. There is a test for it
(`test_a_healthy_echo_does_not_refute_dns_or_mtu_hypotheses`).

**Q: How did you prevent the engine from just reading the answer?**
Three ways: `ProbeRequest` has no fault field, `DiagnosisContext` is built from session
configuration only, and ground-truth columns exist only in `experiment_runs`, written
after a run. Tests assert that injected fault ids do not appear in the diagnostic
payload or the stored diagnosis.

**Q: Isn't the likelihood table just tuned until it works?**
No. The weights are documented protocol-reasoning judgements, not fitted parameters,
and the model was not tuned on the evaluation scenarios. What *was* changed after
seeing intermediate results is the stopping rule's breadth guard — and that change is
documented in `experiment-methodology.md` §4.4, with the before (87%) and after
(99.6%) numbers. If calibration were ever added, the calibration and evaluation
scenarios would have to be disjoint.

**Q: What is the single biggest weakness?**
Model–model circularity: the lab's behaviour and the likelihood table were both
written from the same protocol reasoning, so the evaluation tests whether *probe
selection* helps under this model, not whether the likelihood values are right. The
second is the packet-loss class, where 40% loss can look healthy on a small sample and
the posterior legitimately stays ambiguous.

**Q: Why does the baseline take the same or fewer probes on some classes?**
On classes where the fixed order happens to front-load the decisive probe — port
faults (`TCP_CONNECT` is early) and gateway faults — the two strategies converge or the
baseline is even slightly cheaper. The adaptive planner's advantage is concentrated
where the decisive probe is *late* in the natural order (MTU, link failure), because
it selects by uncertainty rather than by convention.

**Q: Can this run against a real network?**
Not in this build, by design. There is no live-probe implementation; the health
endpoint reports `live_probe_enabled: false` and the API has no endpoint that shells
out to `ping`, `traceroute`, `dig` or a socket. Live probing was listed in the plan as
an optional enhancement to add only after the core passes, and it was not added — this
is recorded as an incomplete item in `limitations.md` rather than implied by a
disabled button.

**Q: What would you do with more time?**
In priority order: repeat-ICMP sampling with an explicit loss estimator to fix the
packet-loss class; a Linux network-namespace adapter so the same probe contract runs
against a real virtualized topology; offline PCAP ingestion as an alternative evidence
source; and a calibration/evaluation split if the likelihoods were ever fitted.
